# RunPod Environment Handoff — 2026-08-18

## 0. Quick Start After Starting a New Pod

**Read this section first** when resuming work after a RunPod restart or migration.

### What persists and what does not

- **Persisted on RunPod Network Volume**: `/workspace/mMIMO_sleep/`, including `.venv/` and all installed Python packages.
- **Not persisted**: system-level packages and linker configuration, such as the system `python3.11` interpreter and the `/etc/ld.so.conf.d/` CUDA compat fix.

Because of this, after a pod restart you will typically see **two** failures unless the steps below are repeated:

1. `.venv/bin/python` fails with `No such file or directory`, because `/usr/bin/python3.11` is missing in the new container.
2. After restoring Python 3.11, PyTorch/Mitsuba may fail to see the GPU with:

```text
Error 804: forward compatibility was attempted on non supported HW
```

### Step 1 — Install system Python 3.11

Run as root inside the new pod:

```bash
apt-get update && apt-get install -y python3.11 python3.11-venv
```

Verify the `.venv` interpreter now resolves:

```bash
/workspace/mMIMO_sleep/.venv/bin/python --version
```

Expected output:

```text
Python 3.11.0rc1
```

**Note**: Ubuntu 22.04 repository currently provides `python3.11_3.11.0~rc1`. The previous pod had `3.11.15`, but the `.venv` `cp311` ABI packages work correctly with this interpreter.

### Step 2 — Re-apply the CUDA library fix

Run as root:

```bash
mv /etc/ld.so.conf.d/00-compat-1958367966.conf \
   /etc/ld.so.conf.d/00-compat-1958367966.conf.bak
ldconfig
```

**Important**: the exact filename may change on each new pod image. Check which compat file is active:

```bash
ls /etc/ld.so.conf.d/00-compat-*
ldconfig -p | grep libcuda.so | head -3
```

Expected output after the fix:

```text
libcuda.so.1 (libc6,x86-64) => /lib/x86_64-linux-gnu/libcuda.so.1
libcuda.so (libc6,x86-64)   => /lib/x86_64-linux-gnu/libcuda.so
```

### Step 3 — Verify the project environment

From `/workspace/mMIMO_sleep`, run:

```bash
.venv/bin/python --version
nvidia-smi
.venv/bin/python - <<'PY'
import torch
print("torch:", torch.__version__)
print("cuda:", torch.version.cuda)
print("available:", torch.cuda.is_available())
if torch.cuda.is_available():
    print("gpu:", torch.cuda.get_device_name(0))
    x = torch.tensor([1.0, 2.0, 3.0], device="cuda")
    print(x ** 2)
PY
.venv/bin/python -m pytest -q
```

Expected final line:

```text
112 passed in ...s
```

### Step 4 — If verification fails

1. Check `nvidia-smi`. If the GPU or driver is missing, the pod itself is misconfigured; re-create it.
2. If `torch.cuda.is_available()` is `False` with **Error 804**, the compat config was probably restored. Repeat Step 2 with the current compat filename.
3. If `.venv` is missing or packages are corrupted, follow the full reinstall instructions in **handoff20260817.md Section 2 and Section 4**.

## 3. Recovery Log — 2026-08-18

### 3.1 Initial Read-Only Check

After pod restart, the following failures were observed **without applying any fixes**:

```text
$ /workspace/mMIMO_sleep/.venv/bin/python --version
bash: /workspace/mMIMO_sleep/.venv/bin/python: No such file or directory

$ ls -l /workspace/mMIMO_sleep/.venv/bin/python3.11
python3.11 -> /usr/bin/python3.11

$ ls /usr/bin/python3*
/usr/bin/python3  /usr/bin/python3-config  /usr/bin/python3-unit2
/usr/bin/python3.10  /usr/bin/python3.10-config
```

Root cause: the `.venv` was created against `/usr/bin/python3.11`, but the new container image only shipped Python 3.10.

### 3.2 CUDA Compat Configuration Was Restored

```text
$ ldconfig -p | grep libcuda.so | head -3
libcuda.so.1 (libc6,x86-64) => /usr/local/cuda-13.1/compat/libcuda.so.1
libcuda.so.1 (libc6,x86-64) => /lib/x86_64-linux-gnu/libcuda.so.1
libcuda.so (libc6,x86-64)   => /usr/local/cuda-13.1/compat/libcuda.so
```

Root cause: same as handoff20260817.md Section 3 — the new pod image re-inserted a forward-compatibility `libcuda.so` ahead of the host driver. RTX 4090 does not support forward compatibility, so this would have produced `Error 804` once Python was restored.

### 3.3 Applied Fixes

1. Installed system Python 3.11:
   ```bash
   apt-get update && apt-get install -y python3.11 python3.11-venv
   ```

2. Disabled the new compat config and refreshed the linker cache:
   ```bash
   mv /etc/ld.so.conf.d/00-compat-1958367966.conf \
      /etc/ld.so.conf.d/00-compat-1958367966.conf.bak
   ldconfig
   ```

**No project dependencies were reinstalled.** The existing `.venv/lib/python3.11/site-packages/` was preserved on the Network Volume and functioned correctly once the interpreter was available.

## 5. Updated Pod Migration Checklist

When moving to a new RunPod instance (or after recreating the container), run:

```bash
# 1. Verify project and venv exist
ls /workspace/mMIMO_sleep/.venv/bin/python

# 2. If Python is missing, install system Python 3.11
apt-get update && apt-get install -y python3.11 python3.11-venv

# 3. Verify the venv interpreter
/workspace/mMIMO_sleep/.venv/bin/python --version

# 4. Verify GPU driver
nvidia-smi

# 5. Verify PyTorch / CUDA
/workspace/mMIMO_sleep/.venv/bin/python - <<'PY'
import torch
print("torch:", torch.__version__)
print("cuda:", torch.version.cuda)
print("available:", torch.cuda.is_available())
if torch.cuda.is_available():
    print("gpu:", torch.cuda.get_device_name(0))
    x = torch.tensor([1.0, 2.0, 3.0], device="cuda")
    print(x ** 2)
PY

# 6. If Error 804 appears, find and disable the active compat config
ls /etc/ld.so.conf.d/00-compat-*
# Then move the active file (replace <filename> with the actual name):
# mv /etc/ld.so.conf.d/<filename>.conf /etc/ld.so.conf.d/<filename>.conf.bak
# ldconfig

# 7. Verify Sionna RT / Mitsuba / Dr.Jit
/workspace/mMIMO_sleep/.venv/bin/python - <<'PY'
from importlib.metadata import version
import mitsuba as mi
import drjit as dr
import sionna.rt
print("sionna-rt:", version("sionna-rt"))
print("mitsuba:", version("mitsuba"))
print("drjit:", version("drjit"))
print("variant:", mi.variant())
PY

# 8. pip consistency check
/workspace/mMIMO_sleep/.venv/bin/python -m pip check

# 9. Run tests
/workspace/mMIMO_sleep/.venv/bin/python -m pytest -q
```

If Step 5 fails with `Error 804: forward compatibility was attempted on non supported HW`, locate the current compat config filename with `ls /etc/ld.so.conf.d/00-compat-*` and move it out of the way, then run `ldconfig`.

## 6. Dependency Reproducibility Risk

Unchanged from handoff20260817.md Section 6. A plain `pip install -e ".[dev,rt]"` from the default PyPI index would resolve to `torch==2.13.0+cu130`, re-introducing the RTX 4090 forward-compatibility failure. Always use the two-step install documented in handoff20260817.md if a full reinstall becomes necessary.

## 7. 本次会话的代码修改记录（2026-08-18）

完成了 `pmi_mask.py` / codebook 模块的增强，从简化单极化模型升级为统一 `ArrayConfig` 的双极化 subarray 版本：

### 新增文件
- `src/mMIMO_sleep/array_config.py` — 统一 `ArrayConfig` dataclass，包含 `num_subarray_rows`、`num_horizontal`、`elements_per_subarray`、`num_polarizations`、`port_order`。
- `tests/test_array_config.py`
- `tests/test_dft.py`
- `tests/test_muting.py`
- `tests/test_pmi.py`

### 重写文件
- `src/mMIMO_sleep/codebook/dft.py` — 基于 `ArrayConfig` 生成 subarray codebook，支持 dual-polarization、`i2` 共相、polarization-major port ordering；修复了 einsum 维度顺序，使 subarray 展开在正确的垂直方向。
- `src/mMIMO_sleep/codebook/muting.py` — 基于 `ArrayConfig` 生成 physical-port muting mask，右半 panel muting 同时作用于两个极化，奇数 `num_horizontal` 抛 `ValueError`。
- `src/mMIMO_sleep/codebook/pmi.py` — `PMI(i11, i12, i2)`，PMI↔beam index 转换（`i2` 变化最快）。
- `src/mMIMO_sleep/codebook/pmi_mask.py` — 基于 array-factor total power 计算 loss；loss 在 normal-state 峰值方向上计算 normal 与 sleep 功率比值。
- `tests/test_pmi_mask.py` — 参数化 `elements_per_subarray ∈ {1,2,3,4}`，新增 loss 与 `i2` 无关、mask 收敛性等测试。

### 更新文件
- `notebook/validate_pmi_muting_patterns.ipynb` — 迁移到新 API，支持 `ArrayConfig`、subarray、双极化、`i2`。

### 关键修复
- `dft.py` 中的 `einsum` 输出维度顺序从 `vrhc` 修正为 `vhrc`，确保 subarray 沿垂直方向展开，物理行顺序正确。
- `pmi_mask.py` 的 loss 改为在 normal-state 峰值方向上同时评估 normal 和 sleep 功率，避免 sleep 主瓣偏移导致的低估。

### Sionna RT integration test（同一会话后续补充）

新增 `src/mMIMO_sleep/simulation/sionna_array.py` 作为 Sionna RT 接口边界：

- `array_config_to_planar_array(config, ...)`：从 `ArrayConfig` 创建 Sionna RT `PlanarArray`；
- `weights_to_sionna_precoding(weights, config)`：将项目 codebook weights 从 row-major 重排为 Sionna RT 的 column-first 元素顺序，返回 `(real, imag)` tuple。

新增 `tests/test_sionna_codebook.py`：

- `test_weights_to_sionna_precoding_reorders_elements`：纯 Python 验证 `weights_to_sionna_precoding` 按 column-first 规则完成 row-major -> column-first 的重排（参数化 `elements_per_subarray=1,2`）；
- `test_array_geometry_matches_array_config`：验证 `ArrayConfig` 位置经显式映射后与 Sionna RT `normalized_positions` 一致（参数化 `elements_per_subarray=1,2`）；
- `test_one_hot_port_mapping_via_channel_phase`：使用 PathSolver 的 LOS 信道相位验证每个 project port index 实际对应 Sionna RT 的正确 physical element 与 polarization（分别对 V/H 极化）；
- `test_codebook_weights_run_in_radio_map_solver`：验证项目 codebook weights 可传入 `RadioMapSolver` 的 `precoding_vec`。

关键发现：Sionna RT 的物理单元编号为 column-first（行/垂直索引变化最快），项目 codebook 使用 row-major（列/水平索引变化最快），二者相差一个转置，所有转换已集中在 `sionna_array.py`。
